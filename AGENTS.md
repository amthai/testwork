# Правила проекта Proof

Эти правила применяются ко всей кодовой базе проекта.

## Рабочие правила

- Перед изменением сначала проверь актуальные документы из `docs/README.md` и связанные спецификации.
- Каноническая документация проекта хранится в `docs/`. Не создавай параллельные каталоги `documentation/` или `documentacion/`.
- Не добавляй секреты, токены, приватные ключи и реальные значения окружения в код, документацию, логи или Git.
- Пиши TypeScript со строгой типизацией. Не используй `any`, если задачу можно решить явным типом или `unknown` с проверкой.
- Общую логику выноси в `src/lib`, переиспользуемые части интерфейса — в `src/components`, экранные композиции — в `src/pages`.
- Сохраняй границы MVP из `docs/product/out-of-scope.md`.
- Не выдавай mock-функциональность за подключённую интеграцию: текущий realtime-транспорт остаётся mock-адаптером.
- Для браузерных разрешений и media API показывай пользователю понятное состояние и возможность повторить запрос.
- Для новых функций и архитектурных изменений сначала зафиксируй решение в спецификации из `docs/superpowers/specs/`, если изменение не является очевидным локальным исправлением.

## Документация и память

- Постоянная документация отвечает на вопрос «как проект устроен сейчас».
- `docs/knowledge/` отвечает на вопрос «что изменили, почему и как проверили».
- После значимого решения, фичи, фикса, теста, рефакторинга, инфраструктурного изменения или заметного изменения документации добавляй одну тематическую запись в `docs/knowledge/entries/YYYY-MM/`.
- Для каждой новой записи обновляй `docs/knowledge/INDEX.md`.
- Для бага обновляй также `docs/knowledge/bugs.md`.
- Пользовательские изменения добавляй в `CHANGELOG.md`; детали реализации оставляй в knowledge-записи.
- Не создавай записи для простого чтения файлов, повторной команды без нового результата и промежуточной диагностики без решения.
- Если изменилось текущее поведение, обнови соответствующий product/technical/QA-документ вместе с записью в журнале.

## Проверки

- После изменений в коде обязательно запускай `npm run build`.
- Для UI-поведения проверяй сценарий вручную в браузере и фиксируй результат в QA-документации или knowledge-записи.
- При добавлении тестового раннера добавь его команду в `package.json` и обнови `docs/technical/setup-local.md`.
- Перед завершением работы проверь отсутствие секретов и случайно добавленных артефактов сборки.

## Git и релизы

- Не создавай Git-коммиты автоматически в обычной работе без явной просьбы пользователя.
- Сообщения коммитов должны кратко описывать результат и не содержать секретов.
- Для пользовательских релизов придерживайся semver: `PATCH` — исправления, `MINOR` — совместимые функции, `MAJOR` — несовместимые изменения.
- Перед релизом синхронизируй код, `CHANGELOG.md`, техническую документацию и результаты QA.
