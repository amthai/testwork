# Knowledge journal

Журнал хранит историю решений и изменений проекта: что произошло, почему выбрали именно этот путь и как проверили результат.

Постоянная документация описывает проект в текущем состоянии. Knowledge-журнал не заменяет её и не должен превращаться в копию исходного кода.

## Структура

| Путь | Назначение |
|---|---|
| `INDEX.md` | Оглавление записей, новые сверху |
| `bugs.md` | Реестр открытых и закрытых багов |
| `_template.md` | Шаблон новой записи |
| `entries/YYYY-MM/` | Датированные записи по месяцам |

## Типы записей

| Тип | Когда использовать |
|---|---|
| `bug` | Найден дефект; запись также отражается в `bugs.md` |
| `fix` | Исправление поведения или ошибки |
| `test` | Значимый QA-прогон или новый результат проверки |
| `question` | Вопрос пользователя с зафиксированным ответом |
| `decision` | Архитектурное, продуктовое или процессное решение |
| `feature` | Новая функциональность |
| `refactor` | Рефакторинг без изменения пользовательского поведения |
| `docs` | Существенное изменение документации или методологии |
| `session` | Итог одной рабочей сессии с несколькими связанными темами |
| `infra` | Сборка, контейнер, деплой, DNS, TLS или инфраструктурная проверка |

## Именование и frontmatter

```text
entries/YYYY-MM/YYYY-MM-DD-short-slug.md
```

Каждая запись начинается с YAML frontmatter:

```yaml
---
date: 2026-09-06
type: docs
area: global
status: done
related: []
---
```

Допустимые значения `status`: `open`, `in_progress`, `done`, `fixed`, `wontfix`, `noted`, `blocked`.

`area` — короткая область проекта, например `global`, `product`, `ui`, `media`, `realtime`, `qa` или `infra`. Не используй закрытый список областей другого проекта.

## Правила ведения

1. Одна тема — одна запись.
2. Запись должна содержать контекст, действие, результат и способ проверки.
3. Новую строку добавляй в начало `INDEX.md`.
4. Для бага указывай номер, статус и ссылку на исходную запись в `bugs.md`.
5. Не копируй большие фрагменты кода; указывай пути к файлам.
6. Если изменение меняет текущее поведение, синхронизируй product/technical/QA-документ.
7. В `CHANGELOG.md` добавляй только краткое описание заметных изменений, а не каждую внутреннюю правку.
