# Technical stack

| Область | Реализация |
|---|---|
| Frontend | React, strict TypeScript, Vite, Tailwind, Fluid Functionalism (Radix/shadcn), Fira Sans Condensed, Motion |
| Media | Media Capture API, AudioWorklet (DeepSeek) или RTCPeerConnection (OpenAI) |
| Backend | Node.js 24, Fastify, strict TypeScript |
| AI | DeepSeek Flash, GigaAM и Яндекс LiveTTS или Piper либо OpenAI SDK, Realtime unified WebRTC interface, server-side WebSocket |
| Feedback | Responses API Structured Outputs, общая Zod-схема |
| Storage | SQLite (node:sqlite), WAL, persistent Docker volume |
| Tests | node:test через tsx, Fastify inject, изолированные test doubles |
| Runtime | Node за HTTPS Nginx, отдельный CPU-контейнер для локальных моделей при выборе DeepSeek |

## Границы модулей

- `src/App.tsx`: координация экранов и сессии.
- `src/lib/api.ts`: same-origin HTTP, ошибки, валидация ответов.
- `src/lib/realtime.ts`: WebRTC, воспроизведение, события и освобождение ресурсов.
- `src/lib/session.ts`: общий контракт сессии, расшифровки и отчёта.
- `src/hooks/use-media-session.ts`: разрешения и media tracks; устаревшие запросы освобождают полученные потоки.
- `src/hooks/use-screen-context.ts`: сжатие и отправка изменившихся кадров с ограничением частоты и таймаутом.
- `server/app.ts`: доступ, cookie, origin/CSRF, лимиты и маршруты.
- `server/provider.ts`: Realtime/Responses API; секрет провайдера не передаётся браузеру.
- `server/sessions.ts`: финализация, отчёт, heartbeat, длительность и подтверждение кадров.
- `server/store.ts`: хранение, дедупликация, выборка кадров, очистка и реестр удалённых calls.
- `src/lib/methodology.ts`: бриф, вопросы, этапы и подробный отчёт; совместимость старых данных через defaults.
- `src/lib/brief-images.ts`, `server/brief-images.ts`: клиентское декодирование/нормализация фото и серверная проверка JPEG.
- `src/lib/preparation.ts`, `src/components/preflight-steps.tsx`: условия переходов и трёхэтапный progress-stepper.
- `src/lib/service-errors.ts`: публичные сообщения недоступности, включая исторические ошибки сессий.
- В `src/lib/roles/` лежат отдельные профили Дениса, Марины, Ирины и Сергея. `team.ts` собирает их в инструкцию планирования и выбирает стиль текущего собеседника для ответа или уточнения. [Файлы ролей](../product/design-lead.md).
- `server/methodology/interview.ts`: очередь Realtime-ходов, plan_turn, этапы и прерывания.
- `server/methodology/validation.ts`: точность цитат, принадлежность оснований, лимиты и fail-closed отчёты.

## Выбор автора вопроса

В плане новой темы модель указывает `interviewerId` и `basisQuote`. Сервер ищет точную непрерывную цитату в исходном тексте задания, распознанном тексте отдельного фото или завершённой реплике участника. Сервер также проверяет, что автор уточнения совпадает с автором последнего вопроса, и применяет общий для команды лимит. Смысловую связь вопроса с фрагментом оценивает модель. Отдельного семантического валидатора в приложении нет. При отсутствии существенного вопроса план `wrap_up` допустим сразу после презентации.

Если автор меняется на специалиста, сервер сначала озвучивает передачу слова от Дениса и дожидается воспроизведения. Только затем специалист задаёт вопрос. Вопрос хранит автора и основание, а произнесённая реплика в расшифровке — автора. В старом журнале вопрос без автора принадлежит дизайн-лиду. Для старых реплик без `speaker` используется прежняя подпись Proof. Версия вновь созданного подробного отчёта — `interview-team-v1`.

## Голосовой режим DeepSeek

`src/lib/local-transport.ts` и `public/proof-mic.js` передают реплики с микрофона в PCM16 16 кГц и получают аудио через same-origin HTTP. Во время озвучки AudioWorklet сравнивает сигнал микрофона с недавним сигналом динамика. GigaAM проверяет фрагмент предполагаемой речи. Подтверждённые слова участника прерывают воспроизведение. Через 0,38 с тишины GigaAM может начать распознавание черновика. Для самостоятельного вопроса об условиях брифа клиент подтверждает окончание после распознавания и как минимум 0,54 с тишины. Обычная пауза около 0,83 с завершает фрагмент, предел непрерывного фрагмента около 25 с. Перед завершением браузер отправляет остаток записи. Сервер сверяет владельца и идентификатор подключения, ограничивает размер и дедуплицирует реплики.

Новый клиент получает длину и содержимое каждого звукового фрагмента прямо в HTTP-ответе на ожидающий опрос. При выборе LiveTTS SpeechKit API v3 принимает текст и голос автора и отдаёт PCM 24 кГц. Первая порция сразу уходит в кодирование, следующие группируются примерно по секунде. Готовый вопрос сохраняет общий контекст интонации. DeepSeek формулирует приветствие и прощание, Яндекс синтезирует текст текущей встречи. Этап meeting отведён для знакомства. Имя участника хранится в participantName сессии и доступно после сокращения контекста или переподключения. В конфигурации с Piper сервер синтезирует фразы локально. Node.js кодирует звук через FFmpeg в Ogg Opus. Браузер последовательно декодирует их и заранее ставит в очередь Web Audio. Для браузеров без Ogg Opus доступен поток WAV-фрагментов, а прежний клиент может запросить целый WAV. При перебивании очередь очищается. Для прямых вопросов об условиях задания DeepSeek получает бриф и последние реплики. Остальные ходы используют общий контекст. Модель может вернуть решение о переходе и план вопроса за одно обращение. Проверка оснований происходит перед озвучкой проверочного вопроса.

Браузер сообщает фактическое начало и конец воспроизведения. Эти события управляют состоянием приветствия. Для реплик участника DeepSeek выбирает действие по схеме из `server/methodology/dialogue.ts`. Встречный вопрос получает отдельный ответ в текущей фазе. Для перехода к формальным вопросам сервер использует существующий план и его проверки.

`server/local-voice.ts` управляет прерыванием и связывает произнесённую реплику с утверждённым вопросом. `speech/service.py` загружает GigaAM при старте и кеширует последнюю использованную модель Piper. `server/deepseek.ts` передаёт план на проверку общей методологии. Последний кадр передаётся в модель при планировании вопроса, для отчёта берётся сохранённая выборка до восьми кадров. Смена провайдера не требует миграции истории.

DeepSeek получает отдельную схему для первого вопроса. До первого ответа статус оценки задаёт сервер. При подготовке отчёта модель получает отдельный список оснований для оценки работы и ответа кандидата. Он включает реплики кандидата и переданные кадры. Если модель вернула варианты формулировок на верхнем уровне, сервер переносит их в раздел подробностей перед общей проверкой цитат. Синтаксические ошибки и несовместимая структура дают восстановимую ошибку формата.

## Потоки данных

До WebRTC: POST /api/briefs принимает text (до 16000 символов, минимум 40 без фото) и images (до 3). Браузер принимает JPG/PNG/WebP до 10 MiB, перекодирует в JPEG до 2048 px по длинной стороне и 1.2 млн символов data URL, без исходных метаданных. Сервер проверяет размер, MIME/data URL, уникальность ID, JPEG-маркеры и размеры до провайдера. Лимит тела 3.7 MB действует только для этого маршрута; внешний URL недопустим. Полное декодирование повреждённого JPEG остаётся у image provider; проверка контейнера не доказывает читаемость изображения.

Текст задания сервер сохраняет напрямую. Для файлов Responses получает input_image и возвращает imageSources с распознанным текстом и описанием по каждому ID. Исходные файлы остаются в памяти браузера. При подготовке итогового отчёта модель выделяет требования по сохранённым текстам. Сервер проверяет дословность цитаты в указанном источнике. Если требования выделить не удалось, отчёт использует исходный текст и разговор. Для старых сессий сохраняется ранее подготовленный список требований.

Сохраняется один бриф на профиль. POST /api/sessions проверяет владельца briefId. При переподключении используется копия из сессии. Для распознавания изображений действуют отдельные дневные и параллельные лимиты. Кнопка «К подключению» отправляет форму и сразу открывает следующий шаг. Изменение материалов сбрасывает сохранённый ID.

В режиме OpenAI Realtime: create_response=false, interrupt_response=true. Сервер создаёт intro/audio → silent presentation → plan_turn/text → validated question/audio → wrap_up/audio → closing/audio. Каждый response помечен metadata; чужие и повторные response.done не меняют этап. Невалидный инструмент получает одну попытку исправления, затем восстановимое прерывание. Незавершённая генерация не оставляет молчаливое зависание. Просьба пояснить вопрос не расходует уточнение. Прерванные реплики помечаются и не служат основанием негативной оценки ответа.

Браузер отправляет SDP серверу; сервер создаёт OpenAI call и возвращает SDP answer. Речь участника и ответ Дениса передаются напрямую по WebRTC. Сервер подключается к тому же call по sideband WebSocket, сохраняет расшифровку и добавляет изображения через conversation.item.create. Для утверждённой реплики другого специалиста `server/expert-speech.ts` получает отдельный MP3 от `gpt-4o-mini-tts`. Браузер воспроизводит его и подтверждает начало и конец, а текст попадает в контекст беседы. При перебивании воспроизведение отменяется.

Кадр учитывается только после conversation.item.added/created. В голосовом контексте остаются последние 6 изображений; SQLite сохраняет равномерную выборку до 24 кадров с первым и последним. Для отчёта выбирается до 8 кадров и сохранённые реплики.

«Завершить» немедленно останавливает воспроизведение и захват устройств и показывает страницу результата. Клиент отправляет остаток речи и вызывает finish. Голосовое завершение дожидается конца прощания. При автоматическом завершении по таймеру сервер допускает до 27 секунд на прощание. Сервер дожидается финальной транскрипции и запускает итоговый отчёт. Генерация отчёта идемпотентна внутри процесса. После рестарта прерванный отчёт можно запросить повторно.

Реестр call ID хранится отдельно. Неудачный hangup повторяется служебным циклом; после рестарта старые calls завершаются до принятия новых запросов. Неактивная вкладка закрывается по heartbeat через 60 секунд, длительность — серверным таймером с шагом 10 секунд.

## Безопасность и эксплуатация

Случайный токен cookie служит capability устройства; в БД хранится SHA-256. Переданные клиентом transcript/feedback не принимаются. Материалы не считаются инструкциями для модели. При составлении отчёта сервер отсеивает выводы с ошибочными ссылками, изменёнными цитатами или критикой ответа на непрозвучавший вопрос. После удаления сводка и советы собираются из проверенных наблюдений. Обоснованность интерпретации проверяется при экспертном чтении.

Производственный контур требует HTTPS и код доступа. Cross-origin изменения запрещены, для записи нужен специальный заголовок. Доверие к одному proxy hop разрешается только при закрытом upstream-порте за Nginx. Запросы и секреты не логируются; ошибки содержат только операционные метаданные.

Квота сохраняет внутренний код quota, но UI и API error показывают «Сервис временно недоступен. Попробуй ещё раз немного позже». Старые сообщения о балансе нормализуются схемой при чтении сессий. До создания звонка не обещается сохранённая сессия.

SQLite рассчитан на одну реплику. При масштабировании понадобятся общее хранилище и распределённые лимиты/очередь. Семплирование кадров не является видеозаписью.
