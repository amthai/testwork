# Proof: рабочая Defense Session

Дата: 2026-09-06. Основание: пользователь поручил довести продукт до рабочего состояния и предоставил ключ OpenAI для подключения.

Сценарий интервьюера и формат отчёта уточнены следующей согласованной [спецификацией методологии](2026-09-06-design-lead-methodology.md): обязательный бриф, серверные этапы, адаптивные вопросы и подробный разбор. Она имеет приоритет над первоначальным описанием VAD/тона ниже.

## Решение и границы

Реализуем полный текущий сценарий: подготовка → голосовая защита с контекстом экрана → разбор → повторное открытие результата. Это расширяет прежнюю границу mock MVP. Существующий визуальный язык сохраняется; состояния интерфейса отражают события соединения и реальный результат.

Варианты: прямой WebRTC с серверным управлением выбран ради низкой задержки и контроля сессии; проксирование всего аудио через сервер добавляет транспортную сложность; цепочка STT/LLM/TTS увеличивает задержку. Отдельный vision-запрос на каждый кадр не нужен: Realtime принимает изображения напрямую.

## Архитектура

- React/Vite frontend, Fastify/TypeScript backend, Node 24.
- POST создания сессии: сервер принимает SDP и создаёт OpenAI Realtime call через unified interface. Постоянный API-ключ доступен только серверу.
- Серверный WebSocket sideband сохраняет завершённые реплики от OpenAI, принимает кадры через авторизованный HTTP endpoint и добавляет их в голосовой контекст. Идентификаторы событий предотвращают дубли.
- Микрофон и воспроизведение ответа работают через WebRTC. Статусы говорят/слушают/подключение основаны на событиях. Автоплей с явной кнопкой повторного включения звука при блокировке браузером.
- Semantic VAD low и инструкция спокойного интервьюера: приветствие, презентация, уточнение окончания, по одному вопросу, пользователь может перебивать ответ.
- Кадры JPEG ограниченного размера отправляются приблизительно раз в 5 секунд при изменении изображения, не вызывают голосового ответа сами по себе. Сервер хранит ограниченную равномерную выборку и подтверждённое число кадров.
- После завершения микрофон и экран останавливаются; сервер завершает call и ждёт финальные реплики. Responses API создаёт структурированный разбор с привязкой к существующим ID реплик. Недостаток данных, отказ модели и ошибка API имеют отдельные состояния и повторную попытку.

## Данные и доступ

SQLite в отдельном persistent volume достаточен для текущего одного VPS/одной реплики. Храним сессии, расшифровки, выбранные JPEG и отчёты; сырые аудио/видео не записываем. PostgreSQL потребуется при горизонтальном масштабировании. Гостевой профиль определяется случайной HttpOnly cookie; сервер хранит её хеш. Чужой session ID не даёт доступа к данным. Пользователь видит историю на этом устройстве, скачивает текстовый отчёт и удаляет свою сессию.

В production доступ к платному AI защищён серверным кодом доступа. Лимиты создания на IP/профиль, общий дневной лимит и лимит параллельных вызовов ограничивают расход; максимальная длительность контролируется сервером и завершает OpenAI call. Heartbeat закрывает брошенные вкладки. Код доступа и секрет провайдера не попадают в сборку. Cross-origin изменения запрещены; origin берётся из конфигурации, proxy trust ограничен.

Срок хранения 7 дней с автоматической очисткой. Перед началом явно сообщается о передаче голоса/кадров OpenAI и хранении расшифровки/отчёта; отдельный чекбокс не требуется. Аккаунты между устройствами, оплата и тарифы требуют отдельного коммерческого решения и в эту реализацию не включаются.

## Надёжность

Таймауты запросов, понятные сообщения ошибок и ручное переподключение с сохранённым контекстом. При отказе экрана доступен разговор без него; повторное подключение доступно во время созвона. После перезагрузки доступен сохранённый результат, зависший вызов завершается heartbeat timeout. Генерация отчёта идемпотентна, повторное нажатие не создаёт дублирующих запросов. Сбой сервера переводит незавершённые сессии в прерванные.

## Реализация и проверки

1. Контракты данных, конфигурация, SQLite, OpenAI адаптер и управление жизненным циклом.
2. Защищённый API, серверные лимиты, реальные состояния frontend, история и отчёт.
3. Проверки изоляции пользователей, ограничений, ошибок провайдера, восстановления и дедупликации на node:test; test doubles разрешены только внутри тестов.
4. Production build и отсутствие ключа в assets, npm audit, ручные проверки в браузере и реальные минимальные обращения OpenAI.
5. Контейнеры и инструкции запуска; проверка candidate до публикации. Текущий production не считается обновлённым до подтверждённого развёртывания.
