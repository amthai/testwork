# Proof: три шага подготовки и фотографии задания

Дата: 2026-09-06. Основание: прямой запрос пользователя на реализацию.

С версии 0.7 сценарий сохранения задания и переход к устройствам описаны в [актуальной спецификации](2026-11-25-assignment-and-voice-controls.md). Далее зафиксирован первоначальный сценарий 0.2.

## Сценарий и интерфейс

Вместо общей длинной формы — три экрана внутри preflight: «Задание», «Подключение», «Подготовка». Вверху нумерованный progress-stepper. Переход дальше: после анализа задания, затем после подключения микрофона. Экран необязателен. Финальная кнопка запуска существует только на третьем шаге. Уже доступные шаги можно открыть через stepper; назад — без потери черновика и media streams. Новое изменение материалов отменяет прежний анализ и блокирует переход дальше до повторного анализа. Разрешения браузера запрашиваются только явным действием на втором шаге. На третьем — советы по структуре рассказа, приватности и короткое описание созвона.

Сохраняется текущий спокойный визуальный язык Proof. Чёткий заголовок каждого шага, одна основная кнопка внизу, доступные подписи и фокус на заголовке при переходе. Без нового редизайна остальных страниц. Черновик живёт в памяти вкладки, не в localStorage; обновление страницы его сбросит.

## Фото и реальные данные

До трёх JPEG/PNG/WebP по 10 MiB исходного размера, текст до 16000 символов; без фото минимум 40 символов. Можно только фото. Браузер декодирует, корректирует ориентацию средствами image decoder и перекодирует в JPEG до 2048 px по длинной стороне, максимум 1.2 млн символов data URL на файл, без исходных метаданных. Есть превью, удаление, понятные ошибки формата/размера и состояния подготовки/анализа. Batch не добавляется частично при ошибке.

Сервер отдельно ограничивает /api/briefs до 3.7 MB; проверяет схему, число, уникальность ID, размер и JPEG-контейнер до вызова провайдера. Не принимает внешние URL. Responses API получает текст + реальные input_image в одном запросе. Строгий ответ включает распознанный текст и краткое описание каждой картинки; требования ссылаются либо на исходный текст, либо на конкретный источник-картинку. Цитаты проверяются по тексту соответствующего источника. Это проверка согласованности OCR, а не доказательство точности распознавания пикселей; пользователь видит распознавание и ограничения. Нечитаемые/неясные детали не достраиваются в требования.

Исходные JPEG используются только во время анализа и остаются превью в памяти браузера. Proof не сохраняет файлы: в брифе/сессии хранит имена, ID, распознанный текст и описание. Эти данные входят в контекст вопросов и отчёта и экспорт. Вызовы не переносят base64 в Realtime-контекст или polling. Бриф 24 часа; копия вместе с сессией по текущему retention. Изображения задания не считаются доказательством выполненной работы. Старые брифы читаются через defaults.

## Недоступность

Провайдерская квота/биллинг не раскрываются в пользовательском сообщении: «Сервис временно недоступен. Попробуй ещё раз немного позже». Код quota сохраняется для диагностики. Не обещаем сохранённый созвон при ошибке до его создания. Старые сохранённые сообщения о балансе также нормализуются при чтении. Ошибка не удаляет черновик, повтор анализа доступен. Runtime не подменяет отказ мок-результатом.

## Проверка

Автотесты: текст/фото/смешанный ввод, пределы и невалидные изображения до AI, источники/цитаты, старые брифы, отсутствие base64 в БД/сессии, нейтральные ошибки, существующие regressions. npm run build. Браузер desktop/mobile: все три шага, блокировки, назад, сохранение/удаление фото, ошибка/повтор, микрофон и опциональный экран, финальный старт. Изолированные fixtures только в тестах; качество живого распознавания остаётся отдельным gate после доступности API. Production и оплата не входят в эту задачу.

API-контракт: [OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision).
